Organización del Proyecto C-TDS (Hernán Jara)
=============================================

TDS-HernanJara/
├── Makefile                 # Automatiza la compilación (bison, flex y gcc) y la ejecución de tests
├── README.md                # Instrucciones rápidas para compilar y correr los casos de prueba
├── src/                     # Código fuente del compilador (.c, .l, .y)
│   ├── main.c               # Punto de entrada: procesa los flags (-o, -target, -opt, -debug)
│   ├── scanner/
│   │   └── Gramatica.l      # Especificación para Flex (Analizador Léxico)
│   ├── parser/
│   │   └── Gramatica.y      # Especificación para Bison (Analizador Sintáctico y armado del AST)
│   ├── ast/
│   │   └── ast.c            # Funciones para crear nodos, encadenar listas, imprimir y liberar el AST
│   ├── semantic/
│   │   ├── tabla.c          # Implementación de la Tabla de Símbolos (pila de niveles)
│   │   └── typecheck.c      # Recorrido semántico, chequeo de las 14 reglas y anotación de tipos
│   ├── ir/
│   │   └── ir.c             # Generación de Código Intermedio de Tres Direcciones (cuádruplas)
│   ├── asm/
│   │   └── codegen.c        # Traducción del Código Intermedio a Assembly x86-64
│   └── opt/
│       └── optimizer.c      # Pasadas de optimización sobre el Código Intermedio (-opt)
├── include/                 # Cabeceras (.h) que comunican las etapas entre sí
│   ├── ast.h
│   ├── tabla.h
│   ├── typecheck.h
│   ├── ir.h
│   ├── codegen.h
│   └── optimizer.h
├── build/                   # Archivos generados al compilar y ejecutable final (c-tds)
├── tests/                   # Baterías de prueba divididas por cada etapa del compilador
│   ├── 01_scanner_parser/
│   ├── 02_semantic/
│   ├── 03_ir/
│   ├── 04_asm/
│   └── 05_opt/
└── Docs/                    # Documentación de diseño de cada etapa e informe final


¿Por qué armé esta estructura de carpetas?

1. Separar `src/` e `include/`:
   Aislar las cabeceras `.h` de las implementaciones `.c` me permitió mantener interfaces limpias entre etapas. Por ejemplo, cuando el generador de código intermedio (`ir.c`) necesita leer el árbol, solo incluye `ast.h` sin depender de los detalles internos de `ast.c`.

2. Una carpeta por cada etapa en `src/`:
   Como el proyecto de la materia es incremental, dividir `scanner/`, `parser/`, `ast/`, `semantic/`, `ir/`, `asm/` y `opt/` me ayudó a trabajar de forma ordenada etapa por etapa sin terminar con un único archivo gigante difícil de depurar.

3. Directorio `build/`:
   Todo lo que generan Flex y Bison automáticamente (`lex.yy.c`, `Gramatica.tab.c`, `Gramatica.tab.h`) va a parar a `build/` junto con el binario `build/c-tds`, manteniendo limpias las carpetas de código fuente.

4. Suites de `tests/` separadas por etapa:
   Como el 70% de la evaluación pasa por los casos de prueba, organicé una carpeta por cada entrega (`01_scanner_parser` hasta `05_opt`) conectadas al `Makefile` para verificar rápido que ningún cambio nuevo rompa lo que ya andaba de etapas anteriores.
