1. Elección de un Nodo Genérico Ternario (`ASTNode`)
----------------------------------------------------
Para construir el Árbol de Sintaxis Abstracta (`include/ast.h` y `src/ast/ast.c`), decidí diseñar un **Nodo Genérico** (`struct ASTNode`) tal como vimos en las clases de teoría (`05-TDS-AST.pdf` y `07-TDS-ASTyTS.pdf`).

Cada nodo del AST tiene:
- `TipoNodo tipo`: un `enum` que identifica qué representa el nodo (`NODE_PROGRAMA`, `NODE_DECLARACION`, `NODE_METODO`, `NODE_BLOQUE`, `NODE_ASIGNACION`, `NODE_IF`, `NODE_WHILE`, `NODE_RETORNO`, `NODE_LLAMADA`, `NODE_OP_BINARIA`, `NODE_OP_UNARIA`, `NODE_NRO`, `NODE_BOOL`, `NODE_ID`).
- `int linea`: guarda el número de línea del archivo fuente donde apareció esa construcción, para poder dar mensajes de error semánticos precisos.
- `Simbolo *simbolo`: puntero a una estructura con `tipo_dato`, `nombre_id` y `valor`.
- `hijo1`, `hijo2`, `hijo3`: tres punteros a subárboles hijos. La mayoría de los nodos usan uno o dos hijos, pero la sentencia `if (...) Bloque else Bloque` necesita los tres (`hijo1` = condición, `hijo2` = rama `then`, `hijo3` = rama `else`).
- `ASTNode *siguiente`: puntero al próximo elemento cuando el nodo forma parte de una lista.

¿Por qué elegí un Nodo Genérico en lugar de un `struct` distinto para cada construcción?
- Simplifica muchísimo el `%union` de Bison en `Gramatica.y`: todos los no terminales devuelven `ASTNode *`, evitando tener que castear punteros de distintos tipos en C.
- Como desventaja menor (trade-off), un nodo hoja como `NODE_NRO` tiene los punteros `hijo1..hijo3` en `NULL`, ocupando unos pocos bytes de más en memoria, pero para el tamaño de los programas en C-TDS ese costo es despreciable frente a la claridad que gana el código para recorrer, imprimir y liberar el árbol.


2. ¿Un único AST para todo el programa o un AST suelto por función?
-------------------------------------------------------------------
Antes de programar las acciones en Bison evalué dos alternativas:
- Opción A: Guardar las variables globales directo en la Tabla de Símbolos desde el parser y armar un AST separado por cada función.
- Opción B (la que elegí): Construir **un único AST global** cuya raíz es `NODE_PROGRAMA` (`raiz_ast`), de donde cuelgan todas las declaraciones globales y los métodos.

Elegí la Opción B porque desacopla completamente el análisis sintáctico del semántico: `yyparse()` se dedica únicamente a validar la sintaxis y dejar armado el árbol en `raiz_ast`. Si hubo algún error léxico o sintáctico, el compilador frena ahí; si no hubo errores, le pasa `raiz_ast` a `analizar_semantica(raiz_ast)`.


3. El patrón Primer Hijo / Siguiente Hermano (puntero `siguiente`)
------------------------------------------------------------------
Para representar listas de longitud variable (lista de declaraciones globales, lista de parámetros de un método, lista de declaraciones locales, lista de sentencias de un bloque y lista de argumentos de una llamada), usé el puntero `siguiente` de cada `ASTNode` junto con la función `agregar_a_lista(lista, nuevo)`.

En lugar de crear nodos intermedios artificiales para encadenar secuencias, el padre apunta al primer elemento de la lista (por ejemplo, `NODE_BLOQUE->hijo1` apunta a la primera declaración local y `NODE_BLOQUE->hijo2` a la primera sentencia), y los demás elementos se recorren con un simple `for (ASTNode *n = lista; n != NULL; n = n->siguiente)`.

Además, para resolver declaraciones múltiples en una misma línea como `int a, b, c;`, la regla `ListaId` primero encadena los tres nodos `NODE_DECLARACION` con `tipo_dato = NULL` y, al reducirse `VarDecl : Tipo ListaId ;`, llamo a `asignar_tipo_lista($2, $1)` para copiar `"int"` en todos los nodos de esa lista.
