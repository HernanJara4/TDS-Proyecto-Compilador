**Decisiones de diseño: Analizador Sintáctico (Gramatica.y)**

**1. Modificación de la gramática de declaraciones globales**

La especificación define `program → var_decl* method_decl*`. Implementada de forma literal, esa regla produce 3 conflictos shift/reduce en bison, uno por cada token `int`, `boolean` y `float`.

*Causa.* Al terminar la lista de variables globales, el parser tiene un token de tipo por delante y debe decidir entre dos acciones:

- Shift: el tipo inicia otra declaración de variable.
- Reduce: se cierra la lista de variables y el tipo es el tipo de retorno del primer método.

Ambas son válidas con el mismo token. Lo que las distingue es el token que sigue al identificador: `,` o `;` para una variable, `(` para un método. Como LALR(1) usa un solo token de anticipación, no puede decidir en ese punto. Con la resolución por defecto de bison (shift), el parser rechazaría programas válidos que comienzan con un método, como el ejemplo del enunciado (`int inc(int x) {...}`).

*Solución adoptada.* Se aplicaron dos cambios:

- Se unificaron las dos listas en una sola: `ListaDeclaraciones → ListaDeclaraciones Declaracion | λ`, con `Declaracion → VarDecl | MethodDecl`. Esto elimina el punto de decisión entre las dos listas.
- Se eliminó el no terminal intermedio `TipoRetorno`. `MethodDecl` se escribe con dos alternativas directas: `Tipo ID ( Parametros ) Bloque` y `TIPO_VOID ID ( Parametros ) Bloque`. Si `TipoRetorno` se conserva, el mismo conflicto reaparece un paso más abajo, porque el parser debe decidir con `ID` como lookahead si reduce `Tipo → TipoRetorno` o shiftea el identificador.

Con estos cambios, después de `Tipo` la única acción posible es shiftear `ID`, tanto para variables como para métodos. El token siguiente a `Tipo ID` distingue los casos sin ambigüedad: `,` o `;` para variable, `(` para método. La gramática resultante no genera conflictos.

*Consecuencia.* La gramática ya no exige que todas las variables globales precedan a todos los métodos; pueden intercalarse. Esto no altera la semántica del lenguaje, porque la regla 2 del análisis semántico ("ningún identificador es usado antes de ser declarado") controla el orden relevante. Si se requiriera el orden estricto, puede verificarse en la etapa semántica sin modificar la gramática.

*Alternativas evaluadas y descartadas:*

- Resolución por defecto de bison: rechaza programas válidos.
- Precedencia (`%left`, `%prec`): la decisión correcta depende de lo que aparece dos tokens después, y la precedencia no puede mirar hacia adelante.
- Parser GLR (`%glr-parser`): resuelve el caso sin tocar la gramática, pero agrega complejidad al parser generado y a su depuración.
- Lexer con lookahead propio: requiere un buffer de tokens en `yylex()`, con más código y más riesgo de errores (por ejemplo, en el conteo de líneas).
- Left-factoring de `VarDecl` (con un no terminal auxiliar para el resto de la declaración): se probó y no es necesario. `VarDecl` y `ListaId` se mantienen como en la especificación.

**2. Otras decisiones y asunciones**

- **Sentencia `while`.** Se implementó `while ⟨expr⟩ ⟨block⟩` sin paréntesis, tal como figura en la gramática del enunciado. Se asume que no es una errata; queda pendiente confirmarlo con la cátedra.
- **Precedencia y asociatividad.** Se declaran de menor a mayor según la tabla del enunciado: `||`, `&&`, `==`, `< >`, `+ -`, `* / %`, `!`, menos unario. Los operadores de comparación son `%nonassoc`, ya que encadenarlos no tiene sentido. El menos unario usa el token auxiliar `UMENOS` con `%prec`, porque `-` ya tiene la precedencia de la resta binaria.
- **Ausencia de `else` colgante.** Como `if` y `else` requieren siempre un `Bloque` delimitado por llaves, no existe ambigüedad sobre a qué `if` pertenece un `else`.
- **Recuperación de errores.** La regla `error PUNTO_Y_COMA` en `Sentencia` descarta la sentencia errónea y continúa, lo que permite informar varios errores sintácticos en una misma ejecución. `yyerrok` restablece el estado normal del parser.
- **Manejo de memoria.** El lexer duplica cada identificador con `strdup` y las acciones lo liberan con `free`, porque en esta etapa no se almacenan nombres. Este manejo deberá revisarse al incorporar la tabla de símbolos.
- **Alcance.** Esta etapa solo verifica la sintaxis. No construye AST ni realiza chequeos semánticos (existencia de `main`, tipos, alcance de identificadores), que corresponden a la etapa siguiente.
